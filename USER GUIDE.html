CVM AI / ENGLISH GUIDE

Start here

Understand the pipeline, what you need and the order to check each stage.

Website · Download Windows release · Online setup guide

CVM AI takes a video source, runs a compatible trained detector, selects a target and sends calculated movement through the configured output device. It runs as a Windows x64 desktop application and can receive video over a local network for a two-PC setup.

The launcher is already compiled and included. Open Start CVM.cmd to run it. Users do not need Visual Studio, a compiler, Git or a separate Python installation for the packaged application.

Download and extract

Open the Windows release. Download these four files into the same writable folder:

CVMAI-4.1.4-Windows-x64.zip.001
CVMAI-4.1.4-Windows-x64.zip.002
CVMAI-4.1.4-Windows-x64.zip.003
Extract-release.cmd

Run Extract-release.cmd. It joins the three parts, verifies the complete archive and extracts CVM AI 4.1.4. Keep the numbered parts unchanged until extraction succeeds. Allow space for the downloaded parts, the joined archive and the extracted runtime. Use a new folder when upgrading; the helper refuses to overwrite an existing CVM AI 4.1.4 folder.

GitHub's automatically generated Source code ZIP is not the packaged Windows download and can contain Git LFS pointer files instead of large runtime binaries.

First working configuration

  1. Open Start CVM.cmd. It runs the supplied App/CVM AI.exe launcher beside the matched main executable. Start with one parameter group and leave automatic actions, macros, recoil and optional curves off.
  2. Configure the video source. For a two-PC network source, match the sender's destination to the CVM PC's LAN address and match the protocol/port at both ends. For a capture card, select the actual device and a supported resolution/pixel format.
  3. Put your model in App/models and select that actual file. Match the model family, input resolution and class mapping to its export information.
  4. Select the inference backend: DML for compatible ONNX inference through DirectML, or TRT for NVIDIA TensorRT. A .engine requires a compatible TensorRT/GPU environment. These are backends, not model-format choices.
  5. Configure the output device, its COM port or LAN address/port as applicable, and the activation key for the active group/key profile.
  6. Click Start. Check the pipeline in order: an updating picture, sensible detection boxes, the intended selected target, then controlled output. Stop at the first stage that fails.
  7. Click Save, stop processing, close and reopen from the same folder. Confirm that the selected profile and paths were retained.

See Setup and first use for the full two-PC checklist, model/backend choices and first-run checks.

Setup and first use

From a complete runtime folder to a working source, detector and output.

The normal installation is the Windows release. The C# launcher is already compiled as App/CVM AI.exe; no build step is needed to use it. Start CVM.cmd starts that launcher with the correct working folder.

1. Extract the complete Windows package

Download all three .zip.001, .zip.002 and .zip.003 parts plus Extract-release.cmd from the 4.1.4 release. Put all four files in one writable folder. Do not rename the parts or try to extract each part separately.

Run Extract-release.cmd and wait for its completion message. It joins the archive, checks its SHA-256 and extracts a CVM AI 4.1.4 folder. SHA256SUMS.txt is also available for manual verification. Keep enough free space for the downloaded parts, joined ZIP and extracted application. If the destination already contains an installation, extract into a new folder to preserve it.

Open the extracted folder. It must contain Start CVM.cmd, USER GUIDE.html, Guides and App. Inside App, keep CVM AI.exe, cvm-4.1.4.exe, the DLLs, Qt plugins and runtime data in their supplied locations. The source-code ZIP generated by GitHub is not a replacement for the numbered Windows release assets.

2. Check the Windows prerequisites

Component When it is needed
Windows x64 Required by the application and launcher
.NET Framework 4.x Runs the compiled C# launcher; Microsoft runtime download
Microsoft Visual C++ x64 runtime Install/repair from Microsoft's supported downloads if Windows reports missing MSVCP/VCRUNTIME/CONCRT components
Graphics driver Required by the selected DirectML or NVIDIA TensorRT inference path
Capture/output device drivers Required only for the hardware/backend you select

The release contains the application runtime files. Users do not need to compile the launcher, install a Python development environment or install Git. Do not fix missing runtime errors by mixing individual DLLs from unrelated packages into App.

Open Start CVM.cmd. App/CVM AI.exe is the equivalent direct entry point. The supplied launcher targets the matched 4.1.4 main EXE; if it reports a file/version mismatch, restore the matching files from the release. Ordinary user execution is requested by the launcher; administrator mode is not its default requirement.

3. Choose your video route

The video source supplies pixels; the inference backend processes them. Configure them independently.

Setup Video route CVM configuration
One PC Local desktop to CVM on that PC Intended desktop/region and capture dimensions
Two PCs with network video Source PC sender to CVM PC over LAN Matching OBS UDP/TCP-compatible transport, receive address/port and source dimensions
Two PCs with a capture card Source PC video output to the card on the CVM PC Actual capture device, supported resolution/FPS and pixel format
Device-specific capture Supported capture hardware/SDK to CVM Matching device backend, driver and source settings

For initial setup, use one parameter group. Leave Auto-start, macros, recoil, automatic firing, optional curves and prediction off until capture, detection and output work in sequence.

Two-PC network checklist

  1. Connect both PCs to a network on which they can reach each other. Wired Ethernet helps avoid wireless variation. Identify the CVM PC's LAN IPv4 address, for example using ipconfig on that PC.
  2. Choose CVM's intended UDP or TCP receive mode. Configure a sender compatible with that exact mode on the source PC. OBS by itself does not establish that both sides speak the same transport format.
  3. Set the sender's destination to the CVM PC, and use the same port and protocol at both ends. For example, if the source is 192.168.1.10 and CVM is 192.168.1.20, send to 192.168.1.20 on the port chosen in CVM. These addresses are illustrative, not defaults.
  4. If CVM asks for a local bind/listen address, use its receiving interface or the supported all-interfaces setting. Do not use the source PC's IP as the receiver's local bind address. A loopback address such as 127.0.0.1 reaches only the same PC.
  5. If a machine's firewall blocks the feed, allow only the required application/protocol/port on the appropriate private network. The CVM patch does not configure Windows Firewall or require router port forwarding for an ordinary LAN setup.
  6. Start the sender and inspect CVM's receive/preview state. Confirm changing frames, correct orientation and a stable picture before tuning the detector. If preview is tied to processing, complete the remaining model/output fields before pressing Start.

Network video and a network output device are separate connections. A working video stream does not prove the output device's IP, port or key is correct.

Capture-card checklist

Select the actual card, a resolution/FPS that it supports and a compatible pixel format. Verify the source PC is sending the expected video mode. A black or corrupted picture is a capture/format problem to solve before changing detection thresholds.

Capture dimensions and model input resolution are different values. Match each to its own source; raising either value does not fix a missing feed or incompatible model.

4. Supply and select your model

Trained detector weights are not included. Copy your own compatible model into App/models, or use another stable writable location, then select the actual file in CVM. A default model.onnx entry is only a filename and does not create a detector.

Format Backend/use Requirements
.onnx DML, or a TensorRT build source where supported Compatible exported network, model family, input shape and output layout
.engine TRT TensorRT engine compatible with the GPU, runtime and model settings
.cvm Protected model path Matching key/authorization material; no protected cloud models or keys are supplied

.cvmcache is protected cache data, not a general replacement for ONNX. .cvmscurve and QX prediction/curve files are not detector weights. Export PyTorch training weights such as .pt/.pth to a compatible model format; renaming the file extension is not conversion.

DML and TRT are inference backends

The Target Detect backend dropdown has two choices:

  • DML: DirectML. Choose it for a compatible ONNX model and a supported graphics device/driver.
  • TRT: NVIDIA TensorRT. Choose it for a compatible TensorRT engine, or use CVM's supported ONNX engine-build workflow. Building an engine needs a compatible NVIDIA setup and can take time; retain the source ONNX and build information.

An engine built elsewhere is not automatically portable to your GPU/runtime. If it cannot load, use an engine built for the intended environment or the compatible source ONNX. The release has not yet been validated with a real detector or an engine build.

Match the model settings

Setting Use
Model file Your actual local .onnx or .engine file
Model family The decoder matching the export's output tensor layout
Input resolution The shape/resolution expected by the model
Compute device The supported GPU/device intended for inference
Classes The model's real labels and class IDs
Confidence / NMS Suitable thresholds for the model and scene

Get these details from the model's export configuration or provider. CVM cannot infer compatibility from an extension alone. Wrong box geometry or class IDs often point to a family/export mismatch rather than capture or movement settings.

5. Configure selection and output

Check the active parameter group and activation-key profile. Use only the intended classes and display the FOV/selection marker. Leave head/body fusion and random aim points off until the model's classes and ordinary selection are correct.

Output type Configure before testing
Serial device Actual COM port, required baud rate and device connection
Network device Device LAN address, port and required device key, if applicable
Supported mouse/device integration Correct integration, driver/service and supported hardware
Simulated output, where available Confirm the calculation/status without treating it as a hardware connection test

Set the intended activation key in the selected profile. Keep movement settings conservative for the first check. A detection box alone does not mean output is connected or the activation key is held.

6. Start and verify one stage at a time

Press Start with the intended video feed and model selected, then check:

  1. Picture: the correct feed updates without persistent corruption or freezing.
  2. Detections: boxes and labels correspond to visible objects and remain sensible as the picture changes.
  3. Selection: the intended class/target passes the FOV and profile rules; the aim-point marker is positioned as intended.
  4. Output: the selected activation key produces the intended controlled movement through the configured device.

Stop at the first failing stage. A movement gain cannot fix missing frames; lowering confidence cannot connect a device. Use the troubleshooting guide for the earliest failing checkpoint. Once the baseline works, change speed, damping and prediction one at a time. Add optional actions separately.

7. Save, reopen and maintain

Click Save for the intended group/profile, stop processing and close CVM. Reopen from the same release folder and confirm that the model path, capture route, output connection and active profile were retained. App/arm_config.json is the saved configuration; keep its contents private if it contains device information or keys.

Back up that configuration, your models and custom profiles before upgrades. Extract updates into a fresh folder, keep matching binaries/dependencies together and restore only compatible settings. If paths changed, select them again and Save.

Remote services and local use

The identified vendor account/model HTTP clients, cloud parameter sync, remote trust checks, error uploads and usage reporting are disabled. No server login or protected cloud model is provided. Local profiles, compatible ONNX/TensorRT engine paths and LAN capture/device transports remain in place. No hosts-file edit or global firewall block is installed.

CVM AI / ENGLISH GUIDE

Settings explained

Know what each control changes before you tune your configuration.

The basic flow is video -> detection -> filtering -> selection -> aim point -> movement -> output. Each stage depends on the previous one. This reference explains the controls by function. Availability depends on the selected backend and hardware; use the controls available for your selected setup.

Capture and performance

Capture method selects where pixels come from. Capture width/height define the captured region or source format. Model input resolution belongs to the detector and must match the model. Raising either dimension can increase processing cost; it does not automatically improve a poorly matched model.

An FPS limit caps processing/capture where supported. Unlimited is not necessarily smoother. Use the FPS and latency displays to find whether the bottleneck is source capture or inference before reducing dimensions or changing backends. Preview overlays help diagnose the pipeline but also add display work.

For network sources, check addresses, transport and ports on both ends. For capture cards, use a format the device actually supports. If a picture is corrupted, try a supported alternative format before touching detector settings.

Detection

Setting Meaning What to look for
Backend / device The inference implementation and compute device Model loads and inference runs on a supported device
Model family How the detector's output is interpreted Correct box geometry and class count
Input resolution The tensor size expected by the model Compatibility with the exported model
Confidence Discards boxes below a score Too high misses weak targets; too low admits background detections
NMS threshold Suppresses overlapping boxes Lower usually suppresses overlaps more strongly; too much suppression can remove nearby distinct objects
Maximum detections Limits retained boxes per frame High enough for the scene without keeping unnecessary candidates
TRT precision Engine computation precision, such as FP32/FP16 Compare compatibility, accuracy and latency for the actual model/device

Use the model's export information to choose its family and classes. A renamed extension cannot convert a model. A faster backend cannot supply missing trained weights.

Parameter groups and activation keys

The selected group and selected key profile determine which settings you are editing. Check both before changing anything. Side Button 2, right-click and other bindings can have independent parameters. A top-level Auto Apply/Synced indicator is not a substitute for saving to disk.

Keep one known-working group before creating variations. Give new groups meaningful names and change one item at a time. After saving, reopen and verify that the intended group is active.

Target selection and tracking

Class filters allow only the labels you intend to select. Their numbers come from your detector. FOV gates selection to an area of the preview; show that area while adjusting it. A strict gate may require a box center inside the region, while a relaxed gate may count a box edge, depending on the selected mode.

Priority/scoring decides which eligible detection wins. Hold, switching and lost-target settings influence whether selection stays on one object, changes quickly or waits through a short disappearance. If selection jumps between objects, first check allowed classes and the FOV region, then the switching controls.

Dynamic FOV, where available, changes the selection region after acquisition. Check the overlay to understand its effect rather than assuming a fixed visible radius applies in every state.

Head/body fusion links compatible head and body detections. It requires a detector that supplies those classes and the correct pairing. Incorrect mappings can cause vertical jumps or incorrect aim points. Leave it off if the model has only one relevant class or you do not know the pairing.

Aim point

The aim point is a location within the selected rectangle. Ratio/offset controls move it relative to that box, not to an absolute screen coordinate. Use the preview marker to check the result on both large and small boxes; do not assume a ratio copied from another model points at the same feature.

Random aim-point options deliberately vary the point. Fixed-per-lock and periodically changing modes behave differently. A wider radius adds more movement variation and can reduce precision, especially on small boxes. Keep this disabled while diagnosing basic control.

Movement control

X and Y controls can be adjusted independently. Keep the selected controller mode (such as Fast/Track) consistent while comparing changes.

Control Purpose Typical sign it needs attention
Speed / KP How strongly movement responds to target error Too weak trails behind; too strong overshoots or oscillates
Damping / KD Reduces overshoot/change in movement Excessive damping feels sluggish; too little can leave rebound
Prediction Adds anticipation for moving targets Too much can alternate ahead of and behind the target
Lock strength Changes how tightly the chosen controller follows Can interact with prediction and speed; avoid changing all at once
Deadzone Ignores very small remaining errors Too large stops short; too small may allow tiny corrections/jitter

Tune speed on a simple stationary target first, then damping. Add prediction only after that and compare on a moving target. Add a small deadzone only if tiny corrections remain a problem. Record changes so you can return to the previous group. Use values appropriate for your device, sensitivity and model.

Output and input masking

The output method sends the calculated movement. A valid detection and selected target can exist while output is disconnected or the wrong key is active. Check status and connection before changing movement gains.

Axis/button masking suppresses some physical input when supported by the chosen hardware. Capabilities differ by device. It is distinct from disabling movement on an axis and distinct from recoil/aim axis separation. Leave it off until ordinary output behaves as expected.

Keyboard/strafe/macro controls are separate optional actions. Leave them off during the initial setup and verify their own bindings before enabling them.

Triggerbot / automatic firing

This acts when a target meets a trigger-zone condition. Use the zone preview to check its position and allowed classes. Zone size/shape, activation key and target eligibility come before timing adjustments.

Delay is the wait before firing, random delay adds timing variation, hold duration controls a press length, and interval controls repeated presses. Pulse/burst and continuous-hold modes differ. Automatic ADS adds another input action. Keep these features off while checking basic detection and output.

Recoil compensation

The documented choices are a trajectory script or automatic downward compensation. A script must contain actual movement data: choose a valid profile with movement data.

Automatic mode has a base amount, optional increase over time/shots and limits/initial-shot overrides. Those values depend on the application, sensitivity and output path. Test recoil separately before combining it with tracking. Axis separation can assign recoil to Y and aim control to X, where supported, to reduce competing movement. Check conditions such as Require Target or Require ADS if it does not activate.

Movement curves and QX data

Curves alter the movement path after basic control has been calculated. Sigma/Neural/off modes, curvature, tremor, overshoot and convergence options affect the path in different ways. Add these after the direct movement is stable. Turn them off again if they pull the path away from the intended point.

App/qx_model_library contains movement/prediction data. A .cvmscurve file is movement-curve data. Neither is an object detector.

Crosshair color finder

This locates a crosshair using sampled colors or a color range. Use preview sampling rather than guessing a color. RGB tolerance or HSV ranges affect how broadly colors match; search area and minimum-pixel controls affect false matches. Too broad an area can include similar background colors. Confirm its marker follows the actual crosshair before using it as a reference for other actions.

Small-target enhancement

This optional feature adds weak/small candidates using extra filtering/history. It cannot replace an appropriate detector or correct input resolution. If normal detections are already stable, leave it off. If enabling it introduces irrelevant boxes, revisit its area, confidence and matching-region controls.

Anti-flash / turn-and-return actions

The documented function responds to a configured detection class and performs a turn followed by a return. It needs the correct class ID and functioning output. Timing, direction, movement scale and false-trigger filtering all affect the result. A detector with no such class cannot provide that trigger. Leave it off during baseline setup.

Data collection and training

Data collection saves frames and associated labels for a separate dataset/training workflow. It does not improve the running detector automatically. Review generated labels before training, monitor disk use and turn collection off when finished.

A detector workflow is: collect/review images and labels -> train externally -> export a compatible detector -> load it in CVM. A movement-curve workflow produces movement data instead. Model packaging/encryption changes distribution/protection, not what the detector has learned.

Authorization and protected models

The launcher does not supply model-specific authorization or decryption keys. Treat a protected-model compatibility/authorization error separately from video capture, model path and output connection errors.

Troubleshooting

Find the earliest failing stage and work forward from there.

Find the earliest failing stage: startup -> picture -> boxes -> selection -> output -> saved settings. Later controls cannot repair missing inputs earlier in the flow.

Reporting a problem usefully

Record the version, selected group/key, capture method, backend, model filename/family/input size, output method and the exact error text. State the last checkpoint that worked: picture, boxes, selection or output. A short description of that boundary is more useful than changing many settings at once.

Do not include authorization-export contents, device keys or tickets in a shared problem report. Use a copy of the configuration with those fields removed if sharing settings.

If saving is the only problem

  1. Stop processing and choose the intended group/key.
  2. Save and check whether the configuration file was created or updated in App.
  3. Confirm the folder is writable and that you reopen that same runtime copy.
  4. Back up the file before resetting or trying a fresh configuration.
  5. Restore only a configuration compatible with this 4.1.4 runtime.

Files and maintenance

Keep dependencies together and know what to back up when you upgrade.

Keep the application together

App contains the launcher, main application and required runtime dependencies. Keep its DLLs, Qt plugins, Python files and data folders in their supplied locations. Move or back up the complete folder rather than individual executables.

Your files

Location or type Purpose Maintenance
App/models/ Your trained detectors Add compatible weights and keep their paths stable
.onnx Local exported detector for DML or a supported TRT build Match the expected model family and input/output layout
.engine Local TensorRT detector used with TRT Match the GPU/runtime and retain the model/build context
.cvm / .cvmcache Protected model and related cache Retain matching files and model-specific authorization
App/arm_config.json Saved application settings Back up before resetting or replacing
App/recoil_scripts/ Your recoil profiles Script mode requires actual movement data
App/qx_model_library/ / .cvmscurve Movement or prediction data These are separate from detector weights
Runtime caches Generated acceleration data Rebuild only when needed for the model/runtime

The Source folder contains launcher code and technical documentation. It is useful for inspection or rebuilding; it is not a replacement for the binary application dependencies in App.

Back up and move

Stop processing and close the application before making a backup. Keep your configuration, models, custom scripts and curves. Treat any device keys or authorization files as private.

Move the complete release folder when relocating the application. Select model and data paths again if their locations changed, then save the configuration.

Update

Extract an update into a separate folder and retain a backup of your current setup. Use matching application and dependency files. Restore only compatible settings, models and profiles, then verify the pipeline before relying on the new copy.
