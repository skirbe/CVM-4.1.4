# Setup and first use

The normal installation is the Windows release. **The C# launcher is already compiled as `App/CVM AI.exe`; no build step is needed to use it.** `Start CVM.cmd` starts that launcher with the correct working folder.

## 1. Extract the complete Windows package

Download all three `.zip.001`, `.zip.002` and `.zip.003` parts plus `Extract-release.cmd` from the [4.1.4 release](https://github.com/terrafirma2021/CVMAI/releases/tag/v4.1.4). Put all four files in one writable folder. Do not rename the parts or try to extract each part separately.

Run `Extract-release.cmd` and wait for its completion message. It joins the archive, checks its SHA-256 and extracts a `CVM AI 4.1.4` folder. `SHA256SUMS.txt` is also available for manual verification. Keep enough free space for the downloaded parts, joined ZIP and extracted application. If the destination already contains an installation, extract into a new folder to preserve it.

Open the extracted folder. It must contain `Start CVM.cmd`, `USER GUIDE.html`, `Guides` and `App`. Inside `App`, keep `CVM AI.exe`, `cvm-4.1.4.exe`, the DLLs, Qt plugins and runtime data in their supplied locations. The source-code ZIP generated by GitHub is not a replacement for the numbered Windows release assets.

## 2. Check the Windows prerequisites

| Component | When it is needed |
| --- | --- |
| Windows x64 | Required by the application and launcher |
| .NET Framework 4.x | Runs the compiled C# launcher; [Microsoft runtime download](https://dotnet.microsoft.com/en-us/download/dotnet-framework/net48) |
| Microsoft Visual C++ x64 runtime | Install/repair from [Microsoft's supported downloads](https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist/) if Windows reports missing MSVCP/VCRUNTIME/CONCRT components |
| Graphics driver | Required by the selected DirectML or NVIDIA TensorRT inference path |
| Capture/output device drivers | Required only for the hardware/backend you select |

The release contains the application runtime files. Users do not need to compile the launcher, install a Python development environment or install Git. Do not fix missing runtime errors by mixing individual DLLs from unrelated packages into `App`.

Open **`Start CVM.cmd`**. `App/CVM AI.exe` is the equivalent direct entry point. The supplied launcher targets the matched 4.1.4 main EXE; if it reports a file/version mismatch, restore the matching files from the release. Ordinary user execution is requested by the launcher; administrator mode is not its default requirement.

## 3. Choose your video route

The video source supplies pixels; the inference backend processes them. Configure them independently.

| Setup | Video route | CVM configuration |
| --- | --- | --- |
| One PC | Local desktop to CVM on that PC | Intended desktop/region and capture dimensions |
| Two PCs with network video | Source PC sender to CVM PC over LAN | Matching OBS UDP/TCP-compatible transport, receive address/port and source dimensions |
| Two PCs with a capture card | Source PC video output to the card on the CVM PC | Actual capture device, supported resolution/FPS and pixel format |
| Device-specific capture | Supported capture hardware/SDK to CVM | Matching device backend, driver and source settings |

For initial setup, use one parameter group. Leave Auto-start, macros, recoil, automatic firing, optional curves and prediction off until capture, detection and output work in sequence.

### Two-PC network checklist

1. Connect both PCs to a network on which they can reach each other. Wired Ethernet helps avoid wireless variation. Identify the **CVM PC's LAN IPv4 address**, for example using `ipconfig` on that PC.
2. Choose CVM's intended UDP or TCP receive mode. Configure a sender compatible with that exact mode on the source PC. OBS by itself does not establish that both sides speak the same transport format.
3. Set the sender's destination to the **CVM PC**, and use the same port and protocol at both ends. For example, if the source is `192.168.1.10` and CVM is `192.168.1.20`, send to `192.168.1.20` on the port chosen in CVM. These addresses are illustrative, not defaults.
4. If CVM asks for a local bind/listen address, use its receiving interface or the supported all-interfaces setting. Do not use the source PC's IP as the receiver's local bind address. A loopback address such as `127.0.0.1` reaches only the same PC.
5. If a machine's firewall blocks the feed, allow only the required application/protocol/port on the appropriate private network. The CVM patch does not configure Windows Firewall or require router port forwarding for an ordinary LAN setup.
6. Start the sender and inspect CVM's receive/preview state. Confirm changing frames, correct orientation and a stable picture before tuning the detector. If preview is tied to processing, complete the remaining model/output fields before pressing Start.

Network video and a network output device are separate connections. A working video stream does not prove the output device's IP, port or key is correct.

### Capture-card checklist

Select the actual card, a resolution/FPS that it supports and a compatible pixel format. Verify the source PC is sending the expected video mode. A black or corrupted picture is a capture/format problem to solve before changing detection thresholds.

Capture dimensions and model input resolution are different values. Match each to its own source; raising either value does not fix a missing feed or incompatible model.

## 4. Supply and select your model

**Trained detector weights are not included.** Copy your own compatible model into `App/models`, or use another stable writable location, then select the actual file in CVM. A default `model.onnx` entry is only a filename and does not create a detector.

| Format | Backend/use | Requirements |
| --- | --- | --- |
| `.onnx` | DML, or a TensorRT build source where supported | Compatible exported network, model family, input shape and output layout |
| `.engine` | TRT | TensorRT engine compatible with the GPU, runtime and model settings |
| `.cvm` | Protected model path | Matching key/authorization material; no protected cloud models or keys are supplied |

`.cvmcache` is protected cache data, not a general replacement for ONNX. `.cvmscurve` and QX prediction/curve files are not detector weights. Export PyTorch training weights such as `.pt`/`.pth` to a compatible model format; renaming the file extension is not conversion.

### DML and TRT are inference backends

The Target Detect backend dropdown has two choices:

- **DML:** DirectML. Choose it for a compatible ONNX model and a supported graphics device/driver.
- **TRT:** NVIDIA TensorRT. Choose it for a compatible TensorRT engine, or use CVM's supported ONNX engine-build workflow. Building an engine needs a compatible NVIDIA setup and can take time; retain the source ONNX and build information.

An engine built elsewhere is not automatically portable to your GPU/runtime. If it cannot load, use an engine built for the intended environment or the compatible source ONNX. The release has not yet been validated with a real detector or an engine build.

### Match the model settings

| Setting | Use |
| --- | --- |
| Model file | Your actual local `.onnx` or `.engine` file |
| Model family | The decoder matching the export's output tensor layout |
| Input resolution | The shape/resolution expected by the model |
| Compute device | The supported GPU/device intended for inference |
| Classes | The model's real labels and class IDs |
| Confidence / NMS | Suitable thresholds for the model and scene |

Get these details from the model's export configuration or provider. CVM cannot infer compatibility from an extension alone. Wrong box geometry or class IDs often point to a family/export mismatch rather than capture or movement settings.

## 5. Configure selection and output

Check the active parameter group and activation-key profile. Use only the intended classes and display the FOV/selection marker. Leave head/body fusion and random aim points off until the model's classes and ordinary selection are correct.

| Output type | Configure before testing |
| --- | --- |
| Serial device | Actual COM port, required baud rate and device connection |
| Network device | Device LAN address, port and required device key, if applicable |
| Supported mouse/device integration | Correct integration, driver/service and supported hardware |
| Simulated output, where available | Confirm the calculation/status without treating it as a hardware connection test |

Set the intended activation key in the selected profile. Keep movement settings conservative for the first check. A detection box alone does not mean output is connected or the activation key is held.

## 6. Start and verify one stage at a time

Press **Start** with the intended video feed and model selected, then check:

1. **Picture:** the correct feed updates without persistent corruption or freezing.
2. **Detections:** boxes and labels correspond to visible objects and remain sensible as the picture changes.
3. **Selection:** the intended class/target passes the FOV and profile rules; the aim-point marker is positioned as intended.
4. **Output:** the selected activation key produces the intended controlled movement through the configured device.

Stop at the first failing stage. A movement gain cannot fix missing frames; lowering confidence cannot connect a device. Use the [troubleshooting guide](Troubleshooting.md) for the earliest failing checkpoint. Once the baseline works, change speed, damping and prediction one at a time. Add optional actions separately.

## 7. Save, reopen and maintain

Click **Save** for the intended group/profile, stop processing and close CVM. Reopen from the same release folder and confirm that the model path, capture route, output connection and active profile were retained. `App/arm_config.json` is the saved configuration; keep its contents private if it contains device information or keys.

Back up that configuration, your models and custom profiles before upgrades. Extract updates into a fresh folder, keep matching binaries/dependencies together and restore only compatible settings. If paths changed, select them again and Save.

## Remote services and local use

The identified vendor account/model HTTP clients, cloud parameter sync, remote trust checks, error uploads and usage reporting are disabled. No server login or protected cloud model is provided. Local profiles, compatible ONNX/TensorRT engine paths and LAN capture/device transports remain in place. No hosts-file edit or global firewall block is installed.
